## 1. Problem statement (verbatim from organizers)

**Domain:** Cybersecurity & Blockchain
**Title:** Privacy-Preserving Verifiable Identity Network

**Brief Explanation / Real-World Context**
Organizations repeatedly ask users for full identity documents even when they only need one attribute. This increases breach impact and creates unnecessary data copies. Build a system in which a user can prove a claim without disclosing unrelated information.

**Core Challenge**
Design a verifiable-credential architecture supporting issuance, presentation, selective disclosure, revocation and verifier authentication. Demonstrate a realistic claim such as eligibility, age band, employment status or institutional membership.

**Expected 24-Hour Prototype**
Expected prototype: issuer/holder/verifier roles; cryptographic proof; revocation/status mechanism; wallet-like interface; verifier API; audit events.

**Scope, Constraints & Convergence**
Do not place raw personal information on a public ledger. Teams must document trust assumptions and key recovery.
Convergence: Web provides identity workflows; AI can detect suspicious credential patterns; IoT can bind credentials to authorized devices/assets.

## 5. Requirement breakdown (what each phrase must become in our product)

For each item: what it means, how we will demonstrate it, and the test that proves it.

### 5.1 Issuer / Holder / Verifier roles
- **Issuer:** trusted authority (demo: a fictional college or employer) that signs credentials with its private key.
- **Holder:** the user, with a wallet that stores credentials and a holder key.
- **Verifier:** a relying party (demo: a library, a venue, an employer) that requests proof of one claim.
- *Proof:* three separate apps/pages with separate keys; the verifier never talks to the issuer during a normal check.

### 5.2 Issuance
- Issuer creates a credential with a small set of claims (e.g. `student: true`, `age_over_18: true`, `employment_status`, `institution`), signed by the issuer key, and bound to the holder's key.
- Prefer issuing derived facts (`age_over_18`) over raw data (date of birth) where it makes sense.
- *Test:* a credential issued to the wallet verifies against the issuer's public key; a tampered credential fails.

### 5.3 Presentation
- Verifier creates a request: which claim(s), a random one-time challenge (nonce), its own identity. Delivered by QR code or link.
- Wallet shows a consent screen: who is asking, what they asked for, what will NOT be shared. User approves (PIN/biometric style step).
- Wallet returns a presentation containing only the approved claims plus proof of holding the credential, bound to the nonce.
- *Test:* verifier page updates live to verified/denied after the holder approves or declines.

### 5.4 Selective disclosure
- Holder reveals one claim (e.g. age band) while all other claims stay hidden and are not inferable from the presentation.
- Use a proven mechanism (SD-JWT style salted-hash disclosures; BBS+ signatures are an alternative). Verify that the chosen library exists and is maintained. NO custom cryptography.
- *Test:* inspect the presentation payload and show that name, DOB and other claims are absent.

### 5.5 Cryptographic proof
- Three things must be provable: the issuer really signed it, the presenter really holds the credential (holder binding), and the proof is fresh (nonce, short expiry).
- *Test:* replaying a captured presentation fails; presenting to a different verifier fails (audience binding).

### 5.6 Revocation / status mechanism
- Issuer can revoke a credential (e.g. student left). The verifier checks status at verification time.
- Prefer a privacy-friendly approach: a status list (bit-string, like the W3C Bitstring Status List) so the issuer does not learn which credential a verifier is checking. Anchor the status list hash or revocation markers on the chain.
- *Test:* verify OK → issuer revokes → same credential now fails, live in the demo.

### 5.7 Verifier authentication
- The wallet must know who is asking: verifier requests are signed, and the verifier's identity is checked against a registry (can be on-chain) of registered verifiers.
- Wallet shows "Verified verifier: Library X" or a warning for unknown ones.
- *Test:* an unregistered or tampered verifier request is flagged or blocked by the wallet.

### 5.8 Wallet-like interface
- Mobile-friendly web app (PWA), NOT a native app. Credential cards, consent screen, history/audit view, QR scanning.
- Must look polished: UI/UX is scored.

### 5.9 Verifier API
- Documented REST API: create request, get result/status, verify presentation, check status. OpenAPI spec in the repo. This is also what the Convergence Round will call.

### 5.10 Audit events
- Tamper-evident log of: credential issued, request created, consent given/denied, presentation verified/failed, credential revoked, key rotated.
- Logs contain NO raw personal data (use hashes/identifiers). Show a per-user view ("who asked what, when") in the wallet and an operator view for the verifier.
- Optionally hash-chain the log and anchor the head hash on the chain.

### 5.11 Constraint: no raw personal information on a public ledger
- On-chain: issuer public keys / DIDs, verifier registry entries, revocation markers or status-list hashes, audit anchor hashes. Nothing else.
- Off-chain: credentials, claims, personal data.
- We must be able to state in two sentences why each on-chain item is there and why the rest is not.

### 5.12 Documentation we MUST deliver
- **Trust assumptions:** who is trusted for what (issuer, wallet device, verifier, chain, registry), and what breaks if each is compromised.
- **Key recovery:** what happens if the holder loses the phone/wallet key, and if the issuer key leaks. Options to discuss: issuer re-issuance after re-verification, encrypted backup, issuer key rotation with a revoked-keys list.
- **On-chain vs off-chain** table with reasons.
- **Threat model** (section 7) and **limitations** (be honest).

## 6. Convergence ideas (pick what is real, not cosmetic)

- **Web:** identity workflows (onboarding, consent, dashboards) built on our verifier API.
- **AI:** anomaly detection on the audit stream: a verifier asking for more than it needs, bursts of checks on one credential, the same credential presented from many places. We expose an events endpoint an AI team can consume, and accept a risk signal back.
- **IoT:** bind a credential to an authorized device/asset: the holder key lives on the device, and the verifier checks proof-of-possession for a device-bound claim.

## 7. Threats the jury may probe (we must have answers)

| Attack | Our defense |
|---|---|
| Forged credential | Issuer signature check against registered issuer keys |
| Replay of an old proof | One-time nonce + short expiry |
| Proof sent to a different verifier | Audience binding in the presentation |
| Stolen/copied credential | Holder key binding (proof of possession), device PIN |
| Revoked credential still used | Status check at verification time |
| Verifier over-asks for data | Wallet shows exactly what is requested; flag requests beyond need |
| Fake verifier (phishing) | Signed requests + verifier registry; wallet warning |
| Issuer key compromised | Key rotation + revoke old key + re-issue |
| Phone lost | Recovery flow (documented) |
| Linking one user across verifiers | Selective disclosure, no persistent identifiers shared, status-list privacy |

## 8. Pivot readiness (design now, finish in 2 hours)

- **"Stricter auth":** step-up authentication before the wallet approves a sensitive request (WebAuthn/PIN), verifier-side policy for required assurance level, and optional device binding.
- **"Zero-day / vulnerability patch":** issuer key rotation and emergency revocation, a "compromised key" flag in the registry, wallet warning for credentials signed by a compromised key, and a patch path for a vulnerable verification step.
